# مالکیت فایل‌ها و مرز نوشتن تیم‌ها

قاعدهٔ صریح درخواست‌کننده: **agent یک تیم اجازهٔ تغییر یا ویرایش هیچ فایل متعلق به تیم دیگر را ندارد.** خواندن برای تحلیل و review مجاز است؛ ایجاد فایل در پوشهٔ تیم دیگر، حذف، تغییر نام، جابه‌جایی، format، بازتولید با ابزار و اعمال patch نیز نوشتن محسوب می‌شوند. کوچک‌بودن اصلاح یا روشن‌بودن جواب استثنا نمی‌سازد.

## مالکیت در هر پرونده

مسیرهای جدول نسبت به `requests/<request-id>/` هستند مگر ریشهٔ مجموعه یا Backend صریح آمده باشد.

| فایل یا محدوده | مالک نوشتن | رفتار سایر تیم‌ها |
|---|---|---|
| product/، request.md، interview.md، decisions.md | محصول؛ decisions اینجا تصمیم‌های محصول است | فقط خواندن و ثبت اصلاحیه؛ تصمیم فنی در technical ثبت می‌شود |
| qa/، شامل سناریو، coverage، plan و execution | QA | فقط خواندن؛ فنی test-mapping خودش را می‌نویسد و توسعه evidence خودش را می‌دهد |
| technical/ و اسناد طراحی canonical معرفی‌شده در index | فنی | فقط خواندن؛ کدزن برای اصلاح طراحی به فنی بازمی‌گرداند |
| development/ و مسیرهای کد/تستِ صریحاً مجاز در task و Backend | توسعه، پس از اختیار پیاده‌سازی | فنی مشخصات task را در implementation-plan می‌نویسد؛ فایل task اجرایی را توسعه می‌سازد |
| فایل‌های release/runbook عملیاتی خارج مالکیت‌های بالا | تیم انتشار، فقط با scope و مسیر صریح | مالکیت فنیِ سند طراحی با نیاز به انتشار عوض نمی‌شود |
| requests/board.json در ریشه؛ tracking.md، applicability.md، traceability.csv، baselines/، approvals/، receipts/، reviews/، runs/ و changes/ | هماهنگ‌کنندهٔ workflow؛ ثبت کنترل و ارجاع | خروجی و بازخورد تیم‌ها ورودی ثبت است؛ این محل مجوز ویرایش محتوای product/qa/technical/development نیست |
| AGENTS.md، docs/، workflows/، templates/، scripts/، records/ و examples/ در ریشهٔ مجموعه | نگهداری workflow با درخواست صریح تغییر همین مجموعه | تیم پرونده برای عبور از محدودیت، قواعد و قالب‌های عمومی را تغییر نمی‌دهد |

مالکیت فایل‌های canonical بیرون این مجموعه نیز برقرار است: مسیر `backend/.../docs/` که در index مرجع طراحی معرفی شده، متعلق به فنی است؛ مجوز توسعهٔ کد، اجازهٔ اصلاح آن سند نیست. AGENTS و اختیار همان مخزن نیز باید رعایت شوند. دربارهٔ فایل تازه یا قدیمی که مالک آن از این جدول و مدارک معلوم نیست، پیش از نوشتن مالک تعیین شود؛ آن را خودکار «مشترک» ننام.

## فایل‌های کنترلی مشترک

Coordinator یک نقش محدود برای ثبت گردش کار است و مالک اسناد تیم‌ها نیست. در همان اجرای workflow می‌تواند پرونده/قالب‌های **کنترلی** را ایجاد، journal و یافته را ثبت، traceability مشترک را از خروجی تیم‌ها جمع و کارت انتخاب‌شده را طبق گذار معتبر به‌روز کند. این ثبت باید `executor.team=coordination`، node، منبع واقعی و مسیر مجاز داشته باشد؛ انجامش نیازمند agent دائمی جدا نیست.

این نقش حق بازنویسی قرارداد محصول، سناریوی QA، طرح فنی، کد یا پاسخ انسانی را ندارد. agent تیمی برای رفع یافته نقش Coordinator نمی‌گیرد؛ فقط ثبت کنترلیِ محدود می‌تواند در نقش Coordinator انجام شود. در reviews/ و changes/ یافته با تیم گزارش‌دهنده، مرجع و فایل مقصد ثبت می‌شود؛ متن متعلق به تیم مقصد در محل اصلی توسط همان تیم اصلاح می‌شود. approval، receipt، review و journal ثبت‌شده بازنویسی نمی‌شوند؛ تصمیم یا اصلاح تازه رکورد تازه دارد. تغییر کنترل‌فایل مشترک نیز مطابق قاعدهٔ یک writer و با حفظ داده‌های دیگر انجام می‌شود.

## پیش و پس از هر نوشتن

1. تیم فعال از انتخاب کاربر/انتصاب ثبت‌شده تعیین شود؛ نام node به‌تنهایی تیم را عوض نمی‌کند. در `node-run`، `executor.team` و `writeScope.allowedPaths` مشخص شوند؛ هر مسیر باید واقعاً متعلق به همان تیم باشد.
2. مالکیت مسیر واقعی و مقصد symlink، محدودهٔ خروجی node و اختیار درخواست هم‌زمان کنترل شوند. مجازبودن یک مسیر در task، مالکیت تیم دیگر را لغو نمی‌کند. ابزار format یا generator با اثر خارج scope اجرا نشود.
3. نتیجه با وضعیت پیش از کار مقایسه شود؛ تغییر متعلق به کاربر یا عامل دیگر به این agent نسبت داده یا برای پاک‌کردن diff حذف نشود. اگر اثر ناخواسته بر فایل تیم دیگر رخ داد، اجرای وابسته متوقف و اختلاف گزارش شود؛ رفع آن با تیم مالک و بدون overwrite کور انجام شود.
4. خروجی node فهرست مسیرهای واقعاً نوشته‌شده را ثبت کند. pass اعتبارسنجی مستندات جای این بررسی را نمی‌گیرد.

## مسیر اصلاح فایل تیم دیگر

agent گزارش‌دهنده، محل دقیق، مشکل، شاهد، پیشنهاد و معیار اصلاح را به Coordinator می‌دهد. Coordinator اصلاحیه و تیم مقصد را ثبت و کارت را برمی‌گرداند؛ agent گزارش‌دهنده فایل مقصد را ویرایش نمی‌کند. تیم مالک پس از دریافت، اصلاح و review/نسخه‌سازی لازم را انجام می‌دهد. برگشت موفق به همان بستهٔ معتبر و دریافت مجدد متصل می‌شود.

مثال: QA غلط متن product را می‌بیند؛ یافته ثبت و به P04 ارجاع می‌شود، ولی agent QA اجرای P04 را به‌عنوان نویسندهٔ محصول ادامه نمی‌دهد. در T05، QA گزارش testability می‌دهد؛ اصلاح mapping فنی با تیم فنی است. توسعه نیز سناریوی QA را برای عبور تست تغییر نمی‌دهد.

اگر کاربر صریحاً تیم فعال را عوض کند، آن انتخاب با مرجع تازه ثبت و محدودهٔ نوشتن از نو بررسی می‌شود؛ مجوز تیم قبلی به تیم جدید جمع نمی‌شود. انتقال کارت، دعوت به review، پاسخ انسانی تیم دیگر یا اجرای پشت‌سرهم nodeها تغییر تیم محسوب نمی‌شوند. استقلال reviewer و اعتبار gate همچنان جدا لازم‌اند.

این قاعده قرارداد الزام‌آور رفتار agent است؛ مجوز سیستم‌عامل، sandbox یا قفل خودکار فایل با این تغییر ساخته نشده است. checker فعلی مالکیت واقعی همهٔ writeها را enforce نمی‌کند.
