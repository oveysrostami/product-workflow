# طراحی فنی در چارچوب setup پروژه

این قرارداد برای تحلیل، پرسش‌وپاسخ، طراحی و تحویل فنی به مخزن کد هدف است. طبق [setup پروژه](16-project-setup.md)، نگارش فنی در product-workflow است و Backend ثبت‌شدهٔ همسایه فقط خواندنی است. قواعد واقعی از AGENTS، قراردادهای معماری و تصمیم‌های ثبت‌شدهٔ همان مخزن خوانده می‌شوند؛ این مجموعه constitution دیگری تولید نمی‌کند.

## ورودی و اعتبار baseline

در T02، تیم فنی در technical/index.md شناسهٔ repository، revision و وضعیت dirty، مسیر/hash قواعد معماری، edition/profile و تصمیم‌های محلی، وضعیت setup و مسیر/hash record و plan منتخب setup را ثبت می‌کند. فقط اطلاعات غیرحساس یا digest خروجی‌ها ثبت شوند؛ environment، credential و مقدار secret به پرونده کپی نشوند. setup تأییدشده نشان‌دهندهٔ انتخاب‌ها و آماده‌سازی ثبت‌شده است؛ verified بودن هر سرویس خارجی همچنان evidence جدا می‌خواهد.

در scope مستقل Backend، init-project وضعیت و preflight توسعه را بررسی می‌کند؛ پیش از planning، Spec/Plan/Task یا task محصول در آن محیط، check-development لازم است. agent product-workflow این ابزارها یا هیچ کد Backend را اجرا/import نمی‌کند و فقط record/plan و منابع غیرحساس را می‌خواند. setup ناقص با owner و شرط دریافت شاهد معتبر ثبت و به تیم Backend برای setup/recovery همان claim تحویل می‌شود؛ در این workflow رکورد آن حذف، reset، ترمیم یا جعل نمی‌شود.

تهیهٔ نیاز محصول، QA، مطالعهٔ خواندنی و پیش‌نویس اولیهٔ خارج Backend می‌توانند پیش از setup انجام شوند. طرح اولیهٔ وابسته به انتخاب‌های نامعلوم، برای اجرا منطبق یا آماده معرفی نمی‌شود. G-T بستهٔ متصل به Backend و تحویل مستندات T08 به baseline setup قابل اتکا و معماری مشخص نیاز دارند؛ منبع و محدودیت مطالعه ثبت شود. recorded-completed یا تطبیق محدود record/plan معادل اجرای preflight یا سلامت runtime نیست. آماده‌بودن اجرا با verification مستقل گیرنده تعیین می‌شود. غیبت checkout یا setup با owner و شرط ادامه ثبت می‌شود؛ فایل Spec محصول در Backend برای دورزدن این شرط ساخته نمی‌شود.

## پرسش‌های معماری و تصمیم‌ها

پیش از T03/T04 یا پرسش T10، setup و قواعد مربوط به boundary درخواست خوانده و تصمیم‌ها در سه دسته ثبت شوند:

| دسته | نمونه | رفتار agent |
|---|---|---|
| تصمیم موجود و الزام معماری | stack/profile، مرز owner، لایه‌ها، مالکیت داده و transaction، سیاست امنیت و انتخاب‌های ثبت‌شدهٔ setup | مرجع، revision/hash و اثر بر درخواست را ثبت؛ همان تصمیم دوباره به‌عنوان انتخاب آزاد پرسیده نشود |
| انتخاب طراحی در محدودهٔ موجود | قرارداد operation، port، index، recovery و روش آزمون سازگار با قواعد و setup | گزینه‌های واقعاً مجاز و trade-off مطرح؛ پاسخ موجود تکرار نشود و پیشنهاد AI از تصمیم انسان جدا بماند |
| تغییر baseline یا استثنا | تغییر DB/stack، topology ناسازگار، transaction بین ownerها یا حذف الزام امنیت/verification | در طراحی عادی اجرا نشود؛ تعارض، rule، دلیل و اثر ثبت و برای تصمیم صریح صاحب معماری/زیرساخت ارجاع شود |

پرسش فنی باید مرجع محدودیت، تصمیم باز، گزینه‌های مجاز، پیامد، پیشنهاد و دلیل را نشان دهد. نام کلاس و انتخاب متعارف کم‌اثر سؤال محصول نیستند. نیاز تازه به قابلیت زیرساختی برای گیرندهٔ مستقل با task واقعی در چارچوب extensionهای مجاز طراحی می‌شود؛ اگر capability غایب است آن را implemented معرفی نکنید. هیچ گزینهٔ ناسازگار با baseline به‌عنوان انتخاب عادی یا پیشنهاد پیش‌فرض عرضه نشود.

اگر پاسخ انسان با baseline تعارض داشت، پاسخ خام حفظ ولی خودکار به تصمیم قابل اجرا تبدیل نشود. تغییر عمدی معماری پرونده/اصلاحیهٔ فنی با صاحب اختیار، تصمیم مستند و review مربوط می‌خواهد؛ اثر رفتاری، scope یا پذیرش به محصول و اثر سناریو به QA برگردد. نبود ابزار یا رد policy مجوز waiver عمومی، success stub یا دستکاری قواعد نیست.

## نگارش، review و تحویل

هر تصمیم فنی به نیاز/QA یا rule معماری، baseline setup و مسئول تصمیم متصل باشد. اسناد معماری عمومی Backend کپی و به قواعد موازی تبدیل نشوند؛ طرح درخواست فقط تصمیم و delta لازم را شرح دهد. [مالکیت فایل‌ها](08-team-file-ownership.md) برای اسناد canonical کنار کد نیز برقرار است؛ دعوت به review یا اجازهٔ implementation اختیار تغییر سند تیم دیگر نیست.

T05/T06/T12 انطباق تمام targetها و جریان مشترک با همان baseline را بررسی می‌کنند. T07 تأیید طرح را از اختیار آیندهٔ acceptance test، implementation، merge و deploy در اجرای مستقل جدا ثبت می‌کند؛ در scope این workflow هیچ نوشتن Backend مجاز نیست. در SDD فعلی، Spec با status=ready به فایل و method واقعی آزمون نیاز دارد؛ طرح آزمون آینده کافی نیست. نوشتن آزمون پذیرش آینده تغییر کد است و به گیرندهٔ مستقل Backend با scope معتبر تحویل می‌شود؛ agent این workflow آن را نمی‌نویسد. «طرح مصوب»، «آزمون پذیرش موجود»، «change فعال SDD» و «کد verified» وضعیت‌های مستقل‌اند.

در T08 و ورود مستقل گیرنده به D01، منابع setup و قواعد دوباره با digestهای baseline تطبیق داده شوند. تغییر ورودی، source revision یا انتخاب‌های setup نیازمند تحلیل اثر و اعتبارسنجی دوبارهٔ طرح، review، task و evidence متأثر است؛ refresh hash بدون بررسی معنایی کافی نیست. status جاری درخواست در board و وضعیت تسک اجرایی در SDD ثبت می‌شود؛ Coordinator فقط آن‌ها را با منابع واقعی تطبیق می‌دهد.
