# قرارداد برد JSON

[requests/board.json](../requests/board.json) مرجع وضعیت جاری کارت‌های این مجموعه است. تمام agentها برای فهرست و صف تیم‌ها به همین فایل ارجاع می‌دهند. جدول خوانا در پاسخ از JSON ساخته می‌شود؛ برد Markdown جدا نگه‌داری نمی‌شود. JSON منبع approval یا اثبات اجرای node نیست؛ journal، manifest، approval و receipt شواهد آن‌اند.

## ساختار

ریشه شامل `schemaVersion: 1`، آرایهٔ `columns` و آرایهٔ `cards` است. ستون‌ها `id` پایدار و `title` نمایشی دارند؛ شناسه تغییر نمی‌کند مگر با نسخهٔ تازهٔ قرارداد. `cards: []` یعنی هیچ پرونده‌ای ثبت نشده است. پروندهٔ آموزشی یا طراحی همین workflow وارد cards نمی‌شود.

[قالب کارت](../templates/shared/board-card.json) فقط شکل یک عضو cards است؛ placeholderهای آن باید با دادهٔ واقعی جایگزین شوند. کارت با `requestId` پیدا می‌شود، نه شمارهٔ ردیف آرایه؛ شناسه در کل برد یکتا است.

| فیلد کارت | معنا و قاعده |
|---|---|
| requestId / title / modules | شناسهٔ پایدار پرونده، عنوان و فهرست ماژول‌های معلوم؛ ماژول نامعلوم اختراع نشود |
| requestPath / trackingPath | مسیر request.md و تاریخچهٔ جابه‌جایی/اصلاحیهٔ همان پرونده |
| documentPath | سند اصلی مرحله برای بازبینی؛ تا قبل از ایجاد، null |
| columnId / state | ستون نمایشی از columns و state دقیق طبق قرارداد وضعیت‌ها؛ ستون برگشتی یا انتظار جای state مرحله را نمی‌گیرد |
| team / ownerReference | تیم صاحب اقدام و مرجع انتصاب مسئول؛ مرجع نامعلوم null است، نه نام ساختگی |
| action | یکی از start، continue، return، waiting، blocked، done |
| currentNode / nextNode / resumeNode | node جاری، مقصد بعدی و checkpoint ادامه؛ مقدار نامربوط null؛ nodeها باید در graph باشند، nextNode می‌تواند END/HOLD باشد |
| scope / authorizationReference | دامنهٔ کار و مرجع دستور واقعی؛ documentation، implementation، review یا release؛ scope مجوز را از خودش تولید نمی‌کند |
| baselines | product، qa و technical؛ هرکدام null یا شیء شامل manifestPath، approvalPath و receiptPath؛ دریافت ثبت‌نشده receiptPath=null |
| blocker | شرح مانع فعال یا null؛ صاحب رفع، اثر و شرط ادامه در tracking/journal مرجع ثبت شود |
| openReturnIds | شناسهٔ اصلاحیه‌های هنوز بسته‌نشده در tracking؛ شرح کامل دوباره در کارت کپی نشود |
| lastMovementId / journalPath | آخرین حرکت ثبت‌شده در tracking و journal مربوط؛ پیش از ایجاد null مجاز است، کارت آماده بدون شاهد معتبر نیست |

`team` یکی از product، qa، tech، development، review، release است؛ اگر صاحب اقدام هنوز معلوم نیست null می‌ماند و کارت آمادهٔ تحویل نیست. `state` از [جدول وضعیت‌ها](02-state-and-versioning.md) انتخاب می‌شود. JSON مقدار معلوم‌نبودن را با null نمایش می‌دهد؛ این مقدار معادل «بررسی شد و مانعی ندارد» نیست.

همهٔ مسیرها **نسبت به ریشهٔ product-qa-tech-workflow** هستند؛ نه نسبت به requests یا محل JSON. مسیر فایل محلی واقعی می‌آید، بدون scheme، fragment یا `..`. ارجاع محتوای بیرون این مجموعه در اسناد اصلی و manifest ثبت می‌شود؛ کارت به index محلی آن ارجاع می‌دهد. `ownerReference` و `authorizationReference` می‌توانند مرجع پیام یا سند باشند و ادعای مسیر فایل نیستند.

## نوشتن و نمایش

مالک نوشتن برد، Coordinator در محدودهٔ ثبت کنترل workflow است؛ team کارت، صاحب اقدام بعدی را نشان می‌دهد و مجوز نوشتن فایل‌های آن تیم را به نویسندهٔ برد نمی‌دهد. [مرز مالکیت فایل‌ها](08-team-file-ownership.md) برای تمام agentها برقرار است.

1. برای درخواست تازه، نیاز و پروندهٔ واقعی را ثبت و یک کارت از قالب اضافه کن؛ اگر پرونده از قبل کارت دارد، همان requestId به‌روز می‌شود.
2. پس از هر node/تحویل/برگشت، ابتدا journal و مدارک واقعی و سپس رویداد movement در tracking ثبت شوند. state، تیم، node و مرجع آخرین حرکت در کارت JSON به‌روز شوند؛ تاریخچه حذف نشود.
3. فقط یک writer برای برد باشد. پیش از ذخیره، نسخهٔ تازهٔ فایل خوانده و فقط کارت مرتبط تغییر کند؛ کارت دیگر حذف یا با نسخهٔ قدیمی جایگزین نشود. نوشتن فایل کامل از طریق فایل موقت و جایگزینی اتمیک انجام شود تا JSON نیمه‌نوشته باقی نماند.
4. پیش از نمایش و پس از انتخاب کاربر، کارت با شواهد تطبیق داده شود؛ در صورت قطع کار بین journal و JSON، از journal/تاریخچه بازیابی کن. تعارض حل‌نشده از صف آماده خارج و با علت نمایش داده شود.
5. جدول صف از همین JSON با لینک documentPath و requestPath ساخته شود. آمادگی QA/فنی نیازمند قواعد [ورودی تیم](../workflows/00-team-entry.md) است؛ مقدار columnId به‌تنهایی کافی نیست.

فایل JSON، tracking و journal بیرون manifest محتوای تحویلی‌اند تا حرکت کارت hash اسناد مصوب را تغییر ندهد. نسخه‌های قبلی workflow در آرشیو محفوظ‌اند؛ تغییر ساختار برد تأیید نسخهٔ محصول را جعل نمی‌کند.

## اعتبارسنجی و حدود آن

`python3 scripts/validate.py` شکل کلی برد، فیلدهای کارت، یکتایی شناسه‌ها، مقادیر وضعیت/تیم/ستون/node و وجود مسیرهای محلی ارجاع‌شده را کنترل می‌کند. hash و معنای gate، واقعی‌بودن تصمیم انسان، علت برگشت و تطبیق کامل journal هنوز به بررسی Coordinator/مسئول gate نیاز دارند. داشتن JSON معتبر به معنی آماده‌بودن برای مرحلهٔ بعد نیست.
