# قرارداد مشترک اجرای هر node

هر کارت شامل **نوع مجری، ورودی، کار دقیق، خروجی، شرط پایان و مقصد هر نتیجه** است. JSON هم‌ارز در [graph](graph.json) نگه‌داری و کارت‌ها از آن تولید می‌شوند. این فایل‌ها specification هستند؛ engine اجرایی نصب یا پیاده نشده است.

پیش از اجرای پرونده، [ورودی انتخاب تیم](00-team-entry.md) اجرا می‌شود. graph از I01 درخواست تازه را شرح می‌دهد؛ انتخاب پروندهٔ موجود از صف، ادامهٔ checkpoint معتبر است و پرونده/مصاحبه را از ابتدا نمی‌سازد. برای ازسرگیری، journal باید node معتبر، آخرین گذار مجاز، ورودی‌های فعلی و اقدام انجام‌نشده را ثابت کند؛ در نبود آن وضعیت مسدود است. انتخاب تیم و کارت خودش node تصمیم محصول یا approval نیست.

## پیش و پس از node

[مالکیت فایل‌ها](../docs/08-team-file-ownership.md) پیش‌شرط هر نوشتن است. تیم فعال و allowedPaths در node-run ثبت می‌شوند؛ actor یا outputs این کارت مجوز نوشتن در تیم دیگر نیست. اگر مقصد اصلاح متعلق به تیم دیگری است، Coordinator فقط ثبت و تحویل را انجام می‌دهد و agent گزارش‌دهنده منتظر تیم مالک می‌ماند. review، دریافت یا تصمیم انسانیِ تیم دیگر، تیم نویسنده را خودکار عوض نمی‌کند.

قبل اجرا، Coordinator اعتبار input baseline، اختیار actor، prerequisite و نبود writer متعارض را کنترل و attempt را در [node-run](../templates/shared/node-run.json) ثبت می‌کند. بعد اجرا، output/ref/digest، نتیجه، evidence و next node را ثبت می‌کند. فقط یکی از transitionهای همان کارت انتخاب می‌شود. نتیجه‌ای که در کارت نیست success فرض نمی‌شود؛ `blocked` با owner و دلیل ثبت می‌شود.

پس از ثبت journal، [tracking](../templates/shared/tracking.md) و نمای برد به‌روز می‌شوند. اگر next node متعلق به تیم دیگر است، پرونده در صف آن تیم منتظر انتخاب و ورودی واقعی می‌ماند؛ تعیین nextNode به معنی اجرا نیست. در درخواست مستندسازی فنی، T08 خروجی مستندات را کامل ثبت می‌کند و ادامهٔ توسعه بدون اختیار صریح به HOLD با resumeNode=D01 می‌رود.

`AI` نگارش/تحلیل می‌کند، `Human` تصمیم یا دریافت را انجام می‌دهد، `Tool` checker/test را اجرا می‌کند. AI می‌تواند متن تصمیم انسان را ثبت کند ولی نقش اجراکنندهٔ تصمیم همچنان Human است. «review مستقل» نیازمند reviewer متفاوت است؛ session جدید همان نویسنده بدون استقلال، کافی نیست.

## نتایج مشترک همهٔ nodeها

| رخداد | رفتار دقیق |
|---|---|
| ورودی ناقص/منقضی | هیچ خروجی approved تولید نشود؛ `blocked`، owner و input لازم؛ پس از اصلاح همان node با attempt جدید |
| انتظار پاسخ انسان | `waiting-human` با متن سؤال/نسخه و resumeNode؛ سکوت، timeout و گزینهٔ پیشنهادی جواب نیست |
| ابزار قطع/محیط غایب | `blocked` و command/error امن؛ اجرای ناممکن را pass/skip قابل پذیرش نکنید؛ پس از رفع همان node |
| اثر عمل نامعلوم | ابتدا readback؛ تکرار action خارجی/merge/migration ممنوع تا اثر روشن؛ owner مربوط بررسی کند |
| توقف مصاحبه | P04 با موارد باز و وضعیت «آمادهٔ بازبینی با مورد باز»؛ P07 تا رفع یا خروج scope مؤثر پاس نمی‌شود |
| pause صریح | checkpoint و resumeNode؛ توقف کار خواسته‌شده بدون حذف خروجی |
| cancel صریح | وضعیت cancelled، آثار انجام‌شده و تحویل امن؛ لغو، rollback ضمنی نیست |
| تغییر ورودی هنگام اجرا | output به input قدیمی متصل؛ C01 برای impact؛ خودکار به نسخهٔ جدید منتسب نشود |

توقف مشترک edge موفقیت نیست و در نمودارها برای هر node تکرار نشده است. endpointهای graph: `END` پایان scope با receipt، `HOLD` توقف قابل ادامه با owner. خطاهای مستند هر node مسیر اصلاح مشخص دارند. بازگشت به مرحلهٔ قبل تمام کار را از نو شروع نمی‌کند؛ فقط subgraph متأثر دوباره بررسی می‌شود.

## محدودیت retry

خواندن و تحلیل روی input ثابت قابل تکرار است. برای نوشتن از draft/version/diff و یک writer استفاده کنید. برای approval از decision reference و برای اثر خارجی از شناسهٔ همان action و readback استفاده کنید؛ کلید تازه برای retry نامعلوم نسازید. پس از دو چرخه با blocker یکسان، موضوع برای تصمیم صاحب انسانی جمع‌بندی می‌شود. این سیاست برای جلوگیری از حلقهٔ بی‌پایان است، نه اجازهٔ کنارگذاشتن gate.

## بستهٔ تحویل

handover باید خلاصهٔ scope، ترتیب مطالعه، rule/UC/AC و موارد خارج scope، baseline منابع، وضعیت gate، dependency، موارد باز با owner، انتظار از گیرنده و معیار دریافت داشته باشد. approval و receipt در فایل جدا حفظ می‌شوند. لینک دسترسی‌ناپذیر یعنی تحویل کامل نیست؛ ارسال به سامانهٔ بیرونی فقط با اختیار مشخص انجام می‌شود.

## واحدهای ماژولی داخل nodeها

T04 برای هر target متأثر یک workUnit نگارش دارد؛ T06 و V01 برای review هر target و سپس review کل درخواست workUnit جدا دارند. self-loop فقط تا تکمیل فهرست محدود impact-map و جمع‌بندی مشترک ادامه می‌یابد؛ هر عبور output و وضعیت واحد را ثبت می‌کند. تغییر فهرست targetها از C01 می‌گذرد، نه افزودن واحد پنهان.

D01 task بعدی آماده را با dependencyهای بسته‌شده انتخاب می‌کند و D02–D05 آن واحد را اجرا می‌کنند. nodeهای لایهٔ نامرتبط با خروجی N/A مستدل طی می‌شوند؛ target صرفاً سازگاری کد مصنوعی نمی‌گیرد. D05 پس از taskهای محلی، کار آزمون مشترک را ثبت می‌کند و فقط پس از تکمیل evidence لازم به D06 می‌رود. journal شامل workUnit و attempt است؛ تعدد واحدها به معنی مجوز spawn/parallel نیست.
